# 8a: professor-specific drafts from a template and verified facts (ADR-026)

Branch `feat/phase-8a-drafts`, stacked on #50.

## What changed

* `drafts.py`: `generate`, `edit`, `get_draft`, `list_drafts`, `duplicates`,
  `export_payload`, `compose`, `content_hash`, `normalised_body_hash`.
* Migration 16 adds `email_drafts` and `draft_versions` (per-user, cascade),
  with an index on `(user_id, body_norm_sha256)`.
* The account export gains `email_drafts`; the error type is `DraftError`.

## QA points (plan acknowledgement)

1. Approval binding: `content_sha256` over subject, body, recipient and
   attachment is stored per version now. The DB-enforced binding, where any
   change clears approval, lands with approval in 8c.
2. Wording: "Your paper ... caught my interest" or "Your work on ... caught my
   interest". A test asserts no "I read", "I loved", "admire" and similar.
3. Identical bodies: a per-user normalised body hash with an index; the test
   checks the query plan uses `idx_draft_versions_body`.
4. Bounded history: `MAX_VERSIONS = 20`, pruned on every new version (tested
   with 3).
5. Audit: `draft.generated` and `draft.edited` record `version_no` and
   `content_sha256` only (tested).
6. Plain text: no HTML is produced or stored; the 8d screen escapes everything.

## Five priorities

* **Latency:** one draft takes a profile read, one faculty load, one CV version
  and in-memory composition. The duplicate check is one indexed lookup.
* **Data structures:**
  * `UNIQUE (user_id, target_type, target_id)` for drafts;
  * `UNIQUE (draft_id, version_no)` for versions;
  * an index on `(user_id, body_norm_sha256)`.
* **Security:**
  * per-user rows, cascade, and an export;
  * the recipient comes only from a verified, current address;
  * a CV approved for another target is refused;
  * the audit holds no text;
  * plain text only.
* **UX:** a missing detail becomes a flag explaining what to add; edits are
  versioned so nothing is lost.
* **Cost:** no LLM, no network, bounded history.
