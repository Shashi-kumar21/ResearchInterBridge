# 8c: drafts API and exact-content approval (ADR-026)

Branch `feat/phase-8c-drafts-api`, stacked on #52 (8b).

## What changed

* Migration 17 adds `email_approvals`: at most one per draft (`draft_id` is the
  primary key), bound to the approved version and its content hash. Two
  triggers clear it **in the database**:
  * on a new draft version;
  * on any `UPDATE` of a version's subject, body, recipient or
    `cv_version_id`. This includes the automatic NULL set when the attached CV
    version is deleted, which is tested end to end by deleting the CV
    document.
* `drafts.approve(version_no)` performs these checks in order:
  1. the reviewed `version_no` is still current (`draft_changed`);
  2. the recipient is still the professor's verified, current address,
     re-read now (`draft_recipient_unverified`);
  3. no lint finding is blocking (`draft_lint_blocked`; the message lists the
     codes only).

  It then stores a content hash **recomputed from the current row**. A stored
  approval counts only while its version id and recomputed hash still match.
* `drafts.withdraw_approval()` is the undo.
* `drafts.summaries()` builds the list from one join on current versions plus
  one batched name read: no history, no N+1 queries (QA n2 on #51).
* Routes:
  * `GET /api/drafts`;
  * `POST /api/drafts`;
  * `GET /api/drafts/{id}`, which includes live lint and the approval;
  * `PUT /api/drafts/{id}`;
  * `POST /api/drafts/{id}/approve`;
  * `DELETE /api/drafts/{id}/approval`.

  All need a session and are scoped to the account. `DRAFT_RULE` (120 per 5
  minutes) applies to the write routes.
* `DraftError` is mapped: 400 `invalid_draft`, 404 `draft_missing`, and 409
  for `draft_wrong_cv`, `draft_changed`, `draft_recipient_unverified` and
  `draft_lint_blocked`.
* The account export includes each draft's current approval.
* Audit: `draft.approved` records `version_no` and `content_sha256`;
  `draft.approval_withdrawn` records no metadata.

## QA checklist

* The approval binds to a hash recomputed from current state, and the
  recipient is re-checked (tested with a contact marked unverified).
* An edit clears the approval in the database (tested with a direct SQL
  update and with a CV deletion).
* `approve` refuses any blocking finding (tested: codes in the 409 message, no
  draft text).
* The list reads current versions only, with batched names (the response has
  no `history`).
* The write routes are rate-limited; reads are not (tested).
* Strict schemas (extra keys, a 201-character subject and `version_no=0` give
  422) and account scoping (another student gets 404).
* The audit records ids and hashes only (tested).

## Five priorities

* **Latency:** the list is one query plus one batched read; approving does a
  few indexed reads and one upsert.
* **Data structures:** `email_approvals` keyed by `draft_id`; triggers instead
  of application bookkeeping.
* **Security:**
  * exact-content approval enforced by the database;
  * the recipient re-verified at approval;
  * lint gating;
  * account scoping;
  * a rate limit;
  * no text in the audit.
* **UX:** clear 409 codes ("the draft changed; review the latest text") and a
  one-call withdraw.
* **Cost:** no network, no LLM, no background job.

## Tests

`tests/test_api_drafts.py` (15): sessions; generate, lint, approve, list;
edit clears, stale refused, fresh approved; a DB trigger on a direct update; a
CV deletion clears; lint-blocked and unverified-recipient refusals;
